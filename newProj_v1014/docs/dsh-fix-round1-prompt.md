## 2. 缺陷 B：片尾暗环重新出现（时间窗口写反）

**位置**：`src/p7.js` 第 282 行

```js
const gone = ease(at(t, P7.cues.creditsIn, P7.cues.ringGone));
```

`creditsIn = 209.811`，`ringGone = 209.4`，即实际调用 `at(t, 209.811, 209.4)`。

**问题（可推导）**：`phase()` 为 `clamp((t-a)/(b-a))`，此处 `b-a = -0.411`。S56 的时间区间是 `[209.811, 211.957596)`，因此 `t-a ≥ 0`，除以负数恒为负 → 被 `clamp` 到 0 → `gone` 恒为 0 → 第 283 行的 `gone < 1` 永远成立 → **整个 S56 都在以 `alpha=0.3`、`radius=mix(900,1100,0)=900` 绘制一个环**。

而 S55 的环在 209.4 已经衰减到不可见（`decayK` 到 1，`k>=1` 被 `continue` 跳过）。结果是：暗环先消失，再在下一镜整段复活。分镜 S56 明确要求「深蓝底上环**逐渐不可见**」，S55 `exit` 要求「到 209.811 只余暗环与小字注记」。

**要求**：

1. 建立一条**跨镜连续**的环衰减时间线：从 S55 的 `decay = 207.45` 起单调衰减，到 S56 内衰减到 0；跨 209.811 边界时**半径与 alpha 都必须连续**，不能跳变、不能复活。
2. S56 结束时必须是没有任何环的深蓝静帧，字幕留到文件精确结束（211.957596）。
3. 不允许用「反向窗口」这种写法表达衰减；所有时间窗口必须满足 `a < b`。
4. 顺带核对 S55 尾部与 S56 开头的环是否真的「只余暗环」：如果按分镜应在 209.811 保留一点极暗的残余，就让同一条衰减曲线跨过边界，而不是在 S56 另起一条。

**验收**：

- 抽 `207.45 / 208.4 / 209.4 / 209.811 / 210.5 / 211.0 / 211.9` 七帧：环的半径单调不减、alpha 单调不增；`209.811` 前后连续；`211.9` 无环。
- 反向跳转（211.9 → 209.9）与正序渲染同一时刻像素完全一致。
- **注意**：最后一次呼叫的载波路径、触点亮度是否应随环一起退场，请按分镜 S54「青点亮度保持」与 S55/S56 文字自行核对，并在记录里写明结论；如果你判断需要让路径或触点退场，必须给出分镜依据，不要顺手改。

## 3. 缺陷 C：第 5–12 次呼叫没有逐次累积

**位置**：`src/p5.js`

- 第 306–309 行（S39）：`calls = floor((t - ringStart)/callEvery) + 1`，`shown = min(12, …)`。**这里是对的**，S39 内推进到第 4 次。
- 第 368 行（S40）：`const done = i + ring.from <= 10;` —— **与时间无关**，直接把内圈显示 11 个、外圈 7 个失败标记。
- 第 439–442 行（S41）：一次性绘制全部 12 个红点。
- 第 445 行（S41）：`portSeal: 158.6` 封口。

**问题**：S39 结束在第 4 次，S40 一开场就跳到 11 个失败格，S41 又一次性出现 12 个红点。分镜要求的是逐次累积：

- S39：「十二次呼叫**每次沿环前进一格**，前四格只显示返回路径缺失」
- S40：「**第 5 次起**失败格向第二圈堆积」
- S41：「**第 9 次起**轨道向内压缩……**第 12 次**红色端口封闭」

**关键发现（这决定了修法）**：现有 cues 与两拍网格本来就对得上，说明这是漏做累积，而不是时间设计错误。

呼叫完成时刻 `= ringStart + (n-1) × callEvery`，其中 `ringStart = 148.4`，`callEvery = 0.923077`（130 BPM 两拍）：

| 第 n 次 | 完成时刻 | 所属镜头 | 对应设计 |
| --- | --- | --- | --- |
| 1 | 148.400 | S39 | 前四格：只显示返回路径缺失 |
| 2 | 149.323 | S39 | 同上 |
| 3 | 150.246 | S39 | 同上 |
| 4 | 151.169 | S39（止于 151.728） | 同上 |
| 5 | 152.092 | S40 | 起于 151.728，开始向第二圈堆积 |
| 6 | 153.015 | S40 | 同上 |
| 7 | 153.938 | S40 | 同上 |
| 8 | 154.862 | S40（止于 155.421） | 同上 |
| 9 | 155.785 | S41 | 起于 155.421；`cues.compress = 155.7` 与之吻合 |
| 10 | 156.708 | S41 | 向内压缩 |
| 11 | 157.631 | S41 | 同上 |
| 12 | 158.554 | S41 | `cues.portSeal = 158.6` 与之吻合 |

**要求**：

1. 实现**一个**由歌曲时间推导的共享计数器，例如 `callsDone(t) = clamp(floor((t - ringStart)/callEvery) + 1, 0, 12)`，S39/S40/S41 全部引用它，不要各自算。
2. 在任意时刻 t，画面上「已完成的呼叫标记数」必须等于该计数器：不能提前出现、不能一次跳到 11 或 12、不能回退或闪烁。
3. S40 的第二圈堆积、S41 的向内压缩与端口封闭都由这个计数器驱动：**端口不得在第 12 次完成（158.554）之前封闭**；`compress` 与 `portSeal` 若需微调，优先改为从计数器派生，而不是新增 cue。
4. `call n / 12` 之类的画内计数文字必须与计数器一致（当前只在 S39 内计算）。
5. 保持既有设计约束：故障红只标在失败格与越界端口上、**从不整屏铺红**；十二次呼叫是**一圈推进**，不是十二个新构图。

**验收**：

- 抽 12 帧：`148.400 / 149.323 / 150.246 / 151.169 / 152.092 / 153.015 / 153.938 / 154.862 / 155.785 / 156.708 / 157.631 / 158.554`，标记数依次为 1…12。
- 端口封闭只在 `≥158.554` 之后出现；`158.5` 帧尚未封闭、`158.65` 帧已封闭。
- 反向跳转一致性：在同一时刻正序与倒序渲染像素完全相同。
- `diag` 暴露计数器值，供自动核对。

## 4. 缺陷 D：S29 的漂移收住时间反了

**位置**：`src/p4.js` 第 199–204 行

```js
const settle = ease(at(t, P4.cues.settleBack, P4.cues.loopDrift + 1.6));
…
const drift = (1 - settle) * Math.sin((t - P4.cues.loopDrift) * 0.5 + i * 0.7) * 6;
```

`settleBack = 102.6`（第 38 行），`loopDrift = 100.5`（第 37 行），因此 `at(t, 102.6, 102.1)` —— **窗口反向**。

**问题（可推导）**：

- `t < 102.6` 时 `phase` 为正且被 `clamp` 到 1 → `settle = 1` → `drift = 0`：**该漂移的前半段完全不动**。
- `t > 102.6` 时 `phase` 为负 → `clamp` 到 0 → `settle = 0` → `drift = sin(…) × 6`：**该收住的后半段反而在整幅漂移**。

与第 203 行注释「After 100.5s the whole group drifts slowly and then holds the original」正好相反。分镜 S29 也要求「100.5 以后环路继续缓移，**稳定回到原形态**，用户预览关闭」。

另注：即使只把窗口改成正向 `[102.6, 104.2]`，`t < 100.5` 时正弦项本身非零，仍会产生不该有的抖动。所以还需要一个**进入**包络。

**要求**：让三个状态格的可观察行为变成：

1. `t < 100.5`（`loopDrift` 之前）：完全静止，不得有任何横向抖动。
2. `100.5 → 102.6`：缓慢漂移，幅度平滑建立。
3. `102.6 →` 约 `104.2`：单调收住，回到原位并保持不动。
4. 全程确定性：同一时刻反复渲染、反向跳转结果一致，不得依赖累计状态。
5. 允许自行选择缓动形式（例如进入包络 × `(1 - 收住包络)`），但必须在记录里写明表达式和三个时间点的实测幅度。

**验收**：

- 抽 `99.8 / 100.5 / 101.5 / 102.6 / 103.4 / 104.2 / 106.0` 七帧，用现有测量工具（`tools/measure-shot-motion.mjs`）或像素比对给出格位移数值：`99.8` 位移为 0，`101.5` 有可测位移，`≥104.2` 位移为 0 并保持。
- 不引入新的静止帧异常：S29 所在段落的静止帧占比不应比修复前明显恶化（允许在记录中给出前后数值）。

## 5. 系统性要求：让「反向时间窗口」不再静默

缺陷 B 与 D 是同一类错误：`at(a, b)` 传入了 `a > b`，`phase()` 静默 `clamp` 到 0 或 1，画面看起来「有东西在动」，实际语义反了。同一个守卫在上一轮已经抓到过三次真实误用（`route()` 控制点数），这里应该同样处理。

**要求**（至少做一项，两项都做更好）：

1. **运行时守卫**：在共享的时间助手（`src/mv-draw.js` 的 `phase` / `at`，以及 `src/engine/motion.js` 中同名概念）检测 `b < a`，把违规记录进 `window.frameDiagnostics`（例如 `timeWindowViolations`），并保证不抛异常、不打断预览与导出。
2. **静态扫描工具**：新增 `tools/check-time-windows.mjs`，扫描 `src/` 下所有 `at(` / `phase(` 调用点，对可静态求值的字面量窗口报出反向项。
3. 把守卫接入 `npm run check:engine`（或等价的检查脚本），一旦出现违规即判定失败。
4. **扫描全库**并把发现的其它反向窗口一并修掉，在记录里逐个列出（文件、行、修正前后）。如果某项看起来是反向但其实是刻意行为，必须单独说明理由。

> 允许 `b === a` 作为退化情形（宽度为 0 的瞬间），只有 `b < a` 才判为违规。
